# DECISIONS

## Approved / Active Decisions
1. Use a modular monorepo with clear boundaries between Core, adapters, packs, CLI, dashboard, and governance artifacts.
2. Start with contract-first API definitions before runtime implementation.
3. Track architectural decisions in ADRs with explicit status and rationale.
4. Deliver iteratively by controlled phases; do not attempt full-platform implementation in a single change.
5. Use Redis for realtime fan-out, Redis Streams runner-job dispatch, and ephemeral distributed coordination, with PostgreSQL remaining authoritative. Socket.IO runtime, outbox publishing, consumer-group admission/recovery, and durable result idempotency are implemented; runner execution and deployment approval remain pending (ADR-0002, ADR-0005, ADR-0009).
6. Make rank progression Admin-configurable: EXP drives separate Student and staff tracks, staff tiers use English League-style names, rank is non-seasonal, and staff criteria may be role-specific (ADR-0003, revised by `PRODUCT_REQUIREMENTS.md`).
7. Use separate Admin-managed hierarchical categories and tags for learning content; questions have one primary category and multiple tags, category descendant inclusion is explicit, tag filters support any/all, and assignment publication snapshots immutable question versions (ADR-0004, revised by `PRODUCT_REQUIREMENTS.md`).
8. Treat `PRODUCT_REQUIREMENTS.md` as the current source for role-based product behavior. Initial identity provisioning uses audited CSV and email invitations/local authentication; SSO and Moodle are deferred.
9. EXP is the single balance used for two distinct rank tracks (Student and staff), with no seasons; spending EXP may lower rank. EXP/Coin, shop, marketplace, and clan changes are ledgered and audited.
10. Use one primary hierarchical category plus multiple tags for questions; category descendants are included only through an explicit filter option, while tag hierarchy does not implicitly include descendants.
11. The application backend language is Python; the role-based web UI uses Next.js, Tailwind CSS, and Font Awesome. The UI palette/theme must be reviewed through a visual preview before approval.
12. Use Python 3.13, FastAPI, SQLAlchemy 2, and Alembic for the API/persistence foundation, and Next.js 16/React 19/Tailwind 3/Font Awesome 6 for the UI. The Python Socket.IO runtime/client packages are selected and pinned; Redis Streams is selected for runner-job dispatch using the existing Redis client (ADR-0005, ADR-0009).
13. Install dependencies through language package managers as needed and pin them in manifests/lockfiles. Bundle/self-host runtime assets; public CDN, third-party runtime APIs, telemetry, and unapproved public egress are prohibited. Internal LMS APIs remain allowed (ADR-0006).
14. Public resource references must be random and non-sequential. A central backend `ResourceReferenceCodec` uses standard authenticated encryption only for explicitly approved concealment cases; it never replaces authorization or uses custom cryptography (ADR-0006).
15. Use PostgreSQL 17 as the authoritative database and private, self-hosted S3-compatible object storage (MinIO target) for uploaded files. Audit and transactional-outbox records are durable in PostgreSQL; Redis is rebuildable infrastructure (ADR-0007).
16. Use opaque eight-hour browser sessions in `HttpOnly`, `SameSite=Strict` cookies for local API authentication; persist only SHA-256 token digests and CSRF verifiers, use Argon2id password hashes, and require a separate HMAC key for database-backed login throttling. Initial Admin creation is a separate, interactive, one-time CLI operation protected by a PostgreSQL transaction advisory lock and audited atomically. MFA uses AES-256-GCM encrypted TOTP secrets, one-time recovery codes, replay protection, and Admin-managed required-role policy; the stable encryption key is secret-managed and key rotation remains operationally manual.
17. Deliver local-account invitations only through a configured administrator-approved SMTP STARTTLS relay. Persist only a digest of a random, expiring, single-use token; put the bearer token in the email URL fragment so it is not sent in the initial HTTP request. Admin-role invitations are allowed now that MFA enrollment and enforcement exist; if the Admin role requires MFA, the user must enroll before receiving an authenticated session.
18. Use the standalone Python Local Autograder only for explicitly confirmed trusted C, Java, and Python source on a developer's local machine. It is not a sandbox and must never execute learner/untrusted submissions or be wired into LMS/API workers. No student-code execution backend is approved; the previous gVisor proposal is superseded as the initial implementation direction (ADR-0010).
19. Package the Local Autograder as a reusable Python library with a non-executing, configurable static policy analyzer and optional CLI. Static checks are heuristics, not malware detection or proof of safety; execution remains limited to explicitly confirmed trusted source, and the library is not an LMS API execution backend (ADR-0010).
